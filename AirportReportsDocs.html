1. Executive Summary

The Airport Operations Dashboard is a production-ready, multi-tenant web application that transforms raw APVe flight information system data into actionable operational intelligence for airport management teams. It provides eight purpose-built analytical reports covering on-time performance, delay root-cause analysis, gate utilization, taxi time efficiency, baggage handling, and passenger flow — all accessible from a single browser-based interface with no installation required.

Key Value Proposition: Each airport (site) connects to its own APVe data feed, with fully configurable field mappings to accommodate different airport system configurations. A single deployment serves multiple airports with complete data isolation.

The system is built on modern, well-supported open-source technology and is deployed as a containerized application on Azure Container Apps, giving it automatic scaling, zero-downtime deployments, and a low operational overhead. Data is persisted in Azure SQL Database.

2. System Overview and Purpose

Airport operations centers rely on Flight Information Display Systems (FIDS) like APVe to track real-time aircraft movements. However, these systems are optimized for live display rather than analytical reporting. Supervisors and operations managers typically resort to manual exports and spreadsheets to produce the performance metrics required for shift handovers, airline SLA reviews, and regulatory reporting.

The Airport Operations Dashboard solves this problem by acting as an analytics layer on top of the APVe API. It fetches flight movement data for a selected date range, enriches it with computed fields (OTP status, delay band, time period), and presents the results through interactive charts and tables — all within seconds, directly in a browser.

Key Capabilities

  • Multi-site support — One deployment serves any number of airports, each with its own login, data feed, and configuration.
  • Configurable field mappings — Because different APVe installations use different field names, each report's data field names can be customized per site without code changes.
  • Custom report designer — Site administrators can design and publish custom tabular/chart reports by selecting fields, filters, grouping, and aggregation rules.
  • Excel and PDF export — Every report can be exported for offline sharing or archiving.
  • Role-based access — App admins, site admins, and site users have distinct permission levels.
  • Audit trail — Changes to custom reports are recorded in a structured audit log.

Frontend SPA

The React application is a fully client-side SPA. All routing is handled by react-router-dom in the browser. On first load, the application initializes three Zustand stores:

  1. useSiteStore — fetches the list of configured sites from GET /api/sites.
  2. useSessionStore — restores any persisted JWT session from sessionStorage.
  3. useReportsStore — fetches saved custom reports (only after a valid token is available).

The initialization order is carefully sequenced to prevent a 401 error on the reports endpoint before the site token exchange completes. If no session exists, the router redirects to /login.

Express API Backend

The Express server is the single backend process. In production, it simultaneously:

  • Serves the compiled React SPA as static files from /dist.
  • Handles all /api/* routes (auth, CRUD, proxy).
  • Proxies all external APVe API calls through /api/proxy to avoid browser CORS restrictions.

On startup, runMigrations() is called to ensure all required Azure SQL tables exist. gzip compression is enabled via the compression middleware.

APVe Proxy

The /api/proxy route acts as a transparent passthrough to the external APVe flight information API. Requests include the raw body bytes (express.raw middleware, registered before express.json) to ensure binary-safe forwarding without re-serialization. This is important for APVe endpoints that expect a bare JSON string (e.g., a UUID API key) rather than a JSON object.

Database Initialization

The API uses a migration runner (runMigrations() in api/src/db.ts) that executes SQL scripts in order on every startup. Migrations are idempotent (IF NOT EXISTS guards), so restarts are always safe.

5. Authentication & Multi-Tenancy

Authentication Flow

The application supports two distinct authentication paths:

Path A — Site User Login

  1. User submits IATA code, username, and password on the login page.
  2. The API looks up the site record in Azure SQL to get the APVe baseUrl.
  3. The API calls the APVe auth endpoint to obtain an accessToken and publicAccessToken.
  4. The API signs a site JWT containing the site object, token data, user roles, and expiry. This JWT is returned to the browser.
  5. The browser stores the JWT in sessionStorage and attaches it to all subsequent API requests as Authorization: Bearer <token>.
  6. When the APVe publicAccessToken nears expiry, the client uses the stored apiKey to silently refresh it without requiring re-login.

Path B — App Admin Login

  1. User submits username and password on the login page (with Admin toggle).
  2. The API checks the app_admins Azure SQL table and validates the bcrypt-hashed password.
  3. A admin JWT is signed, granting isAppAdmin: true and isGlobalAdmin: true.
  4. The admin can then select any site to act as and switch between sites from the admin panel.

Multi-Tenancy Model

Isolation Guarantee: Each site's data is fetched directly from that site's own APVe instance using that site's credentials. No site can ever access another site's flight data.

Multi-tenancy is enforced at multiple layers:

  • API layer — The site JWT encodes which siteId the user belongs to. All API queries for field definitions and reports are scoped with WHERE site_id = ?.
  • Proxy layer — Flight data is fetched using the APVe baseUrl and tokens from the site's own session — there is no shared credentials pool.
  • Custom reports — Each SavedReport has a siteId owner field. App admin template reports (siteId = null) can be cloned to specific sites.
  • Field configurations — Stored in localStorage under a site-namespaced key, so different users of the same browser each get the correct site's configuration.
  • Audit log — Every change to a report is recorded with siteId, changedBy, and a timestamp.

7. Field Configuration System

Different APVe installations use different field names for the same concepts. For example, the "actual landing time" field might be called actualtime at one airport and actual_arr at another. The Field Configuration System solves this without any code changes or redeployment.

How It Works

  1. Defaults are defined in code. Each report that uses non-standard fields declares a DEFAULTS constant with sensible starting field names (e.g., landingField: 'actualtime').
  2. A settings panel is exposed in the UI. A gear icon opens a collapsible panel with labeled text inputs for each configurable field name.
  3. The user edits and clicks Apply. The component maintains a draft state (live input values) and an applied cfg state. Clicking Apply copies the draft into cfg, which triggers a useMemo recalculation of report data — no page reload needed.
  4. Persistence via localStorage. Applied configurations are saved to localStorage under a key namespaced to the current site ID, e.g., taxitime-cfg-{siteId}. On page revisit, the saved config is restored from localStorage automatically.
Important: Field configuration values are the raw field names as they appear in the APVe JSON response. If the field does not exist in the data, the report will show empty values rather than an error. Users can verify correct field names by checking the Flight Operations raw data table.

Built-in vs. Custom Fields

The system distinguishes between two categories of fields:

CategoryStorageExamples
Built-in fields Defined in DEFAULT_FIELD_DEFINITIONS in types/index.ts linecode, number, adi, gate, schedule, actual, status, delayMinutes, claim, scheduleDate
Site field definitions Azure SQL field_definitions table, scoped by site_id Custom fields created per-site, may include computed expressions (timeDiff, concat, lookup)

Conditional Formatting (Color Rules)

Both built-in and custom fields support color rules — conditional formatting that applies text color, background color, and bold styling to table cells based on the cell value. Rules are evaluated in order; the first matching rule wins.

Built-in color rules example (from status field):

  • On Time → green text on green background
  • Delayed → amber text on amber background (bold)
  • Cancelled → red text on red background (bold)
  • Early → blue text on blue background

Helps operations managers identify systemic delay patterns, peak delay hours, and the most chronically delayed individual flights. Used for root-cause investigation and shift debriefs.

Used in airline partnership reviews and slot coordination.

Gate Utilization /reports/gate-utilization

Purpose & Business Value: Analyzes how effectively each gate/stand is being used throughout the selected period.   • Set default sort order and default filter values

  4. Site users see only active reports in their navigation menu.
  5. All changes are recorded in the audit log with before/after snapshots.

9. Export System

Every report in the dashboard includes an ExportMenu component (top-right corner). Exports are performed entirely client-side — no server round-trip is needed after the data is loaded.

Excel Export (.xlsx)

  • Uses the xlsx library (SheetJS).
  • Creates a workbook with a single worksheet named after the report.
  • Column headers are taken from the report's field labels or column label overrides.
  • All filtered, visible rows are exported (not just the current page if pagination is active).
  • Dates are formatted as strings matching the field's configured dateFormat.
  • File is triggered as a browser download with the report name and current date as the filename.

PDF Export

  • Uses jsPDF + jspdf-autotable.
  • Generates a landscape or portrait PDF with a title header, date range, and site name.
  • Table cells are rendered with autotable, which handles column width distribution and row pagination automatically.
  • KPI summary cards are rendered as a header section above the table where applicable.
Export Tip: For large date ranges, the Excel export is recommended over PDF. PDF rendering is better suited to summary reports (OTP Scorecard, Airline Performance) where the row count is manageable.

13. External APVe API Endpoints

All calls below are made from the browser-side code through the server-side proxy at /api/proxy/{host}{path}. The {baseUrl} placeholder is the APVe base URL configured per site (e.g. https://apve.example.com/). None of these requests ever leave the browser directly — they are forwarded by the Express proxy, which adds no additional authentication of its own.

All five endpoints are reached via POST or GET only. No PUT, PATCH, or DELETE calls are made to the APVe system.
Method Endpoint (relative to {baseUrl}) Auth Request Body / Params Response Purpose
POST authApi/v1/api/Authentication/login None (public) JSON object: { userName, site, password } JSON: { token } (accessToken) Step 1 of login. Validates APVe credentials and returns a short-lived session token.
POST usersapi/v1/api/Users/GetByUserName?expand=activeApiKeys Bearer accessToken JSON string (the username, quoted) JSON: User object with linked activeApiKeys Step 2 (standard flow only). Fetches the user profile and their existing API keys. Skipped when a site serviceApiKey is configured.
POST usersapi/v1/api/UserApiKeys Bearer accessToken JSON object: { userId, activeStart, activeEnd, enabled, siteId } JSON: UserApiKey object (includes key UUID) Step 2b (standard flow only, on-demand). Creates a new API key if the user has none. Only called when GetByUserName returns no active keys.
POST connectpublicapi/api/ConnectPublicApiAuthentication None (public) JSON string (the API key UUID, quoted) JSON: { publicAccessToken } Step 3 of login, and also used for silent token refresh. Exchanges an API key (user's own or site serviceApiKey) for a short-lived publicAccessToken used to query flight data.
GET connectpublicapi/api/ConnectPublicDailies/Dailies Bearer publicAccessToken Query params: scheduleStartTime, scheduleEndTime (ISO datetime strings) XML flight schedule document Primary data fetch. Returns all flight movements for the requested date range. Called on every dashboard/report load and on date-range changes. Retried once on 401/403 (with a fresh token) or on 503/504/timeout.

Authentication Sequence (Standard Flow)

  1. POST authApi/v1/api/Authentication/login → get accessToken
  2. POST usersapi/v1/api/Users/GetByUserName?expand=activeApiKeys → get existing API key UUID (or proceed to 2b)
  3. (if no keys) POST usersapi/v1/api/UserApiKeys → create API key UUID
  4. POST connectpublicapi/api/ConnectPublicApiAuthentication → get publicAccessToken
  5. GET connectpublicapi/api/ConnectPublicDailies/Dailies → flight XML data

Authentication Sequence (Service-Key Flow)

When a site has a serviceApiKey configured, steps 2 and 3 above are skipped:

  1. POST authApi/v1/api/Authentication/login → validates credentials (token discarded)
  2. POST connectpublicapi/api/ConnectPublicApiAuthentication → get publicAccessToken using the site's serviceApiKey
  3. GET connectpublicapi/api/ConnectPublicDailies/Dailies → flight XML data

Token Refresh (Silent)

The publicAccessToken has a ~55-minute TTL. Before it expires, the app silently calls POST connectpublicapi/api/ConnectPublicApiAuthentication again using the stored API key — no user interaction required. The session itself is bounded by an 8-hour hard limit, after which the user must log in again.
